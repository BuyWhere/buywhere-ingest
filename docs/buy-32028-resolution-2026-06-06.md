## Root cause

The live search handler `api/src/routes/products.ts:33-323` (`GET /search`) was
already patched by `e8f407dc` (BUY-31540) to remove `ts_rank(...)` ORDER BY from
its CTE. However, the commit explicitly listed 7 locations across 5 files and
**missed `warmSearchCache` in the same file** (`api/src/routes/products.ts:1037-1051`,
the cache-warm worker that seeds Redis with hot queries at startup).

For broad US queries (`laptop+US` = 70k+ matches), the warm-up CTE materialized
all matching rows before LIMIT, stalling the warm-up and leaving Redis cold.
When the live handler couldn't find a cache entry, it ran the same slow
`ORDER BY id DESC` over 70k+ rows and hit the 20s statement_timeout — returning
the `503 {"error":"Search query timed out","timeout_ms":20000}` the user
observed.

The deployed `dist/routes/products.js` was also stale (still showed
`SEARCH_STATEMENT_TIMEOUT_MS = 20000` and a live `ts_rank` in the warm-up CTE)
even though the source had been updated, because the dist rebuild had not been
re-run after `e8f407dc`.

## Fix

1. `api/src/routes/products.ts:1037-1051` — replaced the `ts_rank`-based CTE in
   `warmSearchCache` with the same `id DESC` Top-N pattern the live handler
   uses (e8f407dc). This brings warm-up latency in line with the live query
   path so Redis actually gets warm on startup.
2. `api/tests/ts-rank-guard.test.mjs` — new regression guard. Walks every
   `.ts` file under `api/src` and fails if any line contains both `ts_rank(`
   and `ORDER BY`. Pinned this regression class in CI; runs in
   `node --test` with no DB needed.
3. `api/dist/**` — full TypeScript rebuild via `(npx tsc; exit 0)` to match
   the Dockerfile. Picked up additional source files that had never been
   compiled (`monitoring/*`, `jobs/dailyKeyReset*.js`, `routes/usage.js`) —
   the dist was significantly stale.
