## Probe loop design

- **Endpoint priority** (per cycle, per domain): `wp-json/wc/store/products`
  (Store API, public on most modern WC) → `wp-json/wc/v3/products` (v3 REST,
  usually auth-gated) → `products.json` (non-Shopify stores that also expose
  this). The Store API is the dominant live endpoint; the v3 REST is mostly
  401/403. The `wp-json/wc/v3` URL was originally in the issue spec, but
  the public Store API is what is actually reachable.
- **Batch & concurrency**: `BATCH_DOMAINS=100`, `PROBE_CONCURRENCY=10`,
  `PROBE_TIMEOUT_MS=8000`, `SLEEP_MS=5000`, `PER_PAGE=20` (the lane-keep-alive
  routine on this workspace has disk at 97% — the loop is therefore
  intentionally low-throughput so it stays out of contention).
- **State**: `data/buy32819-probe-state.json` is updated after every cycle
  with cursor, cycle counter, candidate file, hit count, miss count, and
  product count. The loop reloads the candidate list when the file changes
  (new `candidates_YYYY-MM-DD.jsonl` appears).
- **Ingest path**: Same canonical `buy30331-ingest-stream.mjs` writer, with
  `source='woocommerce'` and `lane='buy32819_non_shopify'`. After the fix
  described below, ingest works end-to-end.
- **Teardown hook**: Every 6th cycle (matching the sustained loop's cadence)
  invokes `scripts/cleanup-teardown.sh` to keep `data/buy32819_non_shopify/`
  from accumulating stale NDJSON. Confirmed in cycle 12: `cycle 12 teardown:
  exit=0 120.0s`.

## Hit rate gap — why 10% is not what Tranco delivers

The acceptance criterion ("≥10% on the Tranco-derived pool") does **not**
match the observed reality on Tranco top-1M, and is not what the historical
WooCommerce lane produces either:

- This run: 4 / 1,600 = **0.25%** (cycles 1–16, top-1M Tranco slice).
- Historical `buy30590-woocommerce-discover.mjs` (per-cycle logs in
  `logs/buy30590_woocommerce_discover.log`): 13 hits / 4,000 probed at
  Tranco offset 20k–30k = **0.325%**. 0 hits in the first 5,000 Tranco
  ranks, 1 hit in the first 10,000. The Tranco top-1M is dominated by
  search engines, social networks, CDNs, news, and government sites that
  will never expose a `/wp-json/wc/store/products` feed.
- 0.25–0.33% is roughly **30× lower** than the 10% target, but **5–7×
  higher** than the 0.04% the exhausted Shopify pool returned in the 15:30
  window referenced in the parent plan.

The lane still meets its risk-diversification goal (different source pool,
different rate-limit pressure, different fail mode), but the per-hour
ingest yield will be far below 150k/hr. The right next step is **not** to
chase 10% on the same Tranco top-1M slice — that target was set without a
hit-rate pilot. The right next step is to **stack the lane with smarter
candidate sourcing** (CommonCrawl `*/wp-json/wc/store/products*` patterns
already in the discovery scripts, the existing
`data/discover_lane_buy30590_woocommerce_merchants.jsonl` from prior runs,
and the `buy31015-known-wc-merchants-v2-progress.json` list) so the loop
is fed candidates that have already been pre-verified as WooCommerce.

## Pre-existing bug found while running this lane

`scripts/buy30331-ingest-stream.mjs` line 298 referenced an undefined
constant `PARALLEL` in the throttle log line. The constant had been
renamed to `THROTTLE_PARALLEL_MAX` everywhere else during the BUY-33198
self-throttle refactor, but the log line was missed. Result: the script
crashed with `ReferenceError: PARALLEL is not defined` on every run,
including the existing sustained and deep-page loops. The disk-pressure
pauses in `data/buy30854-keep-alive-state.json` had been masking this
because the Shopify lanes were not actually trying to ingest.

Fix (one-line): `${PARALLEL}` → `${THROTTLE_PARALLEL_MAX}` in the log
template string. Confirmed by manual ingest of the cycle-3 NDJSON (20
products, exit=0) and the loop's later cycles.

This is a script the issue did **not** list under "do not touch" — the
do-not-touch list is `buy30331-sustained-loop.mjs` and
`buy30590-deep-page-loop.mjs`. The canonical ingest writer was always
intended to be shared.

## Open items for the next heartbeat

1. **Smart candidate feed**: Add a second candidate source — the
   `discover_lane_buy30590_woocommerce_merchants.jsonl` file (live WC
   merchants from the prior run) and the
   `buy31015-known-wc-merchants-v2-progress.json` file — so the probe loop
   is fed pre-verified WC domains alongside the raw Tranco slice. Expected
   hit rate on that feed is ~30–80% per cycle.
2. **Concurrency tuning**: With disk pressure below 95% (currently 97%),
   raise `PROBE_CONCURRENCY` from 10 to 25 and lower `PROBE_TIMEOUT_MS`
   to 6,000 so each cycle drops from ~60s to ~25s.
3. **Re-issue the 10% criterion**: the original acceptance bar is not
   achievable on the raw Tranco top-1M slice. Either retarget to the
   smart-candidate feed (#1) or accept the lane as risk-diversification
   (different source, different failure mode) rather than as a primary
   ingest contributor.
4. **Production deploy**: The systemd unit is ready; production rollout
   is `systemctl daemon-reload && systemctl enable --now
   paperclip-buy32819-probe-loop.service` on the production host. The
   `keepalive` wrapper can be retired once systemd owns the process.
