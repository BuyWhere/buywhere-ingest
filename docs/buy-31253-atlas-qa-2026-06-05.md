## TL;DR

System health monitor (BUY-31178 prevention tool) ran against the Atlas runtime at 2026-06-05T16:20 UTC and returned **overall_status: critical**. The database freshness check timed out on the `products` table, indicating the catalog DB is under stress or the query is too expensive for the configured statement timeout (15s). Runtime API latency and endpoints are healthy.

| Check | Status | Details |

| api_latency | healthy | p95=95ms (threshold: 500ms warning / 1000ms critical) |
| health_endpoints | healthy | All endpoints (db, redis, api_catalog) returned 200 |

## Critical Finding: DB Freshness Timeout

The `db_freshness` check runs:

```sql
SET LOCAL statement_timeout = '15s';
SELECT max(updated_at) AS max_ts FROM products;
```

This times out after 15 seconds, which means either:
1. The `products` table (28M+ rows) is too large for a fast aggregate with the current DB load
2. The DB is under heavy load and cannot complete the query in time
3. There is a long-running transaction or lock contention blocking the query

The transaction errors on subsequent checks confirm the first query's timeout left the transaction in an aborted state.

## Runtime API Health

- `/.well-known/api-catalog`: 200 in 35.0ms
- `/v1/catalog/stats` (indirect via latency check to `/health/db`): p95=95ms

## Open Questions

1. Is the DB timeout a one-time load spike or a chronic issue?
2. Should the `db_freshness` check be optimized (e.g., use `pg_stat_user_tables` instead of full table scan)?
3. Should the statement timeout be increased for this check?

## Required Action

The DB freshness check failure needs investigation. Options:
- Increase `DB_QUERY_TIMEOUT_S` from 15s to 30s
- Switch to `pg_stat_user_tables` for faster freshness estimation
- Investigate DB load and long-running queries

This finding is consistent with BUY-31179 (runtime catalog drift) which identified DB-layer issues in the Atlas/Oracle system.
